# Modal memo state ignores the active profile

The storage pair is profile-scoped, but the Modal control plane is not. `control_dict_name()` is `f"mini-cp-{name}"` and the volume is `app.name` (`src/mini/modal_apparatus.py:70`, `:590`), both keyed by experiment name alone. So a `MINI_PROFILE=dev` run of an experiment that already ran in production finds production's memo records and skips the work it thinks is done, while whatever it does write lands in the dev bucket — a run that reads as memoized and complete with its outputs split across two stores.

Nothing has hit this: it needs a Modal token in a dev-profile session, and the environments that default to `dev` (the Claude Code web env) have Modal off, while the one with Modal (the devcontainer) keeps `dev` opt-in for this reason. So it is latent rather than live — but it is the thing standing between the web environment and a Modal token, which is what would let a web session run experiments rather than only edit code. See `todo/eng/non-prod.md` for how the two environments are configured.

The natural fix mirrors what `PROFILE_KEYS` already does for storage: fold the active profile into the Modal namespace, so `mini-cp-<name>` becomes `mini-cp-<profile>-<name>` under a profile and stays unchanged on the base configuration. That keeps production names and their existing state untouched, needs no discipline from the caller, and gives dev runs their own volume as well as their own memo records. The cheaper alternative — refusing or prefixing experiment names under a profile in `mini run` — leaves the interactive path (a notebook constructing a `ModalApparatus` itself) uncovered, so the naming belongs in `control_dict_name` rather than in the CLI.

Worth checking against `gc` and `mini rm` while doing it: both address the control plane by the same name (`src/mini/gc.py:348`, `src/mini/__main__.py:97`), so they need to resolve the profile the same way or they will look at the wrong dict. `todo/eng/mini-rm-experiment-memo-state.md` is the related gap in deleting memo state at all.

## Notes

**2026-09-06, assessed** — Two things have moved since this was written. The Claude Code web environment now holds a Modal token alongside `MINI_PROFILE=dev` (`./go auth --check` there reports the Modal workspace and a dev-only HF token), so the split is live rather than latent: any `--app modal` run of an existing experiment name from a web session would find production's memo records and write its artifacts to the dev bucket. And Modal's own Environments feature works on this workspace: `modal environment create dev-probe` succeeded (and was deleted again), so it is not gated by plan. An environment namespaces apps, Dicts, Volumes and Secrets, is selected by `MODAL_ENVIRONMENT` or an `environment_name=` argument, and object lookups from inside a container default to the container's own environment, so the worker's `Dict.from_name(dict_name)` follows without changes. That is a cleaner fix than prefixing: the dashboard gets a dev/prod dropdown instead of mixed names, `gc`, `_peek` and `mini rm` need no name mapping, and the shared `mini-hf-cache` Volume is namespaced too (a cold cache on dev, which is fine). The suggested shape: a `modal-environment` key on the profile table, `[tool.mini.profiles.dev] modal-environment = "dev"`, applied by mini before any Modal object is resolved (setting `MODAL_ENVIRONMENT` from the profile is the least invasive way, since the CLI, gc and workers all read it), plus `modal environment create dev` once by hand. Prefixing stays the fallback if a workspace ever can't create environments. The local backend has the same shape of gap: `.mini/<name>` is keyed by name alone too, so a `MINI_PROFILE=dev` local run in a checkout that already ran the experiment under production splits the same way; it is per-checkout and the web env's `.mini` is fresh each session, so it is a smaller hazard, but worth noting when this is fixed.

**2026-09-06, done** — Went with the Environment. `modal-environment` is a third profile key beside the pair (`PROFILE_KEYS` in `src/mini/store.py`), resolved by `modal_environment()` with `MODAL_ENVIRONMENT` winning over the tables, and passed as `environment_name=` at every named lookup: the control-plane `Dict`, `ModalVolume`, the HF cache Volume, the detached and blocking `app.run` contexts, `gc`'s mark phase and the CLI's peek. A `ModalApparatus` built under a profile that names no Environment warns once. `[tool.mini.profiles.dev]` names `dev`, the `dev` Environment exists on the workspace, and `./go auth --check` prints it beside the workspace. Verified live: `bin/mini run --app modal docs/acts/experiment.py` under the dev profile created `mini-cp-acts` and the `acts` Volume in `dev` while `main` kept its own `mini-cp-acts` from June, and the worker's record carries `modal_environment: dev`; the dev state was deleted afterwards. The local backend's matching gap (`.mini/<name>` keyed by name alone) stays as noted above; it is per-checkout, and the web env's `.mini` is fresh each session, so it isn't tracked separately.
